نادرًا ما تفشل واجهة الويب السحابية في يوم إطلاقها. إنها تفشل تدريجيًا. يضيف فريق ثانٍ لوحة جديدة، ويحتاج دور جديد إلى عرض مختلف قليلًا، وتكبر مجموعة بيانات بما يتجاوز ما صُمِّم له الجدول الأول، فتتحوّل لوحة بيانات بدت سريعة في العرض التجريبي إلى واجهة بطيئة وغير متّسقة ويصعب تغييرها.

معظم هذه المشكلات لا تسبّبها المنصّة السحابية خلف الواجهة. تسبّبها قرارات في الواجهة الأمامية كانت معقولة لشاشة واحدة ولم يُعِد أحد النظر فيها مع نمو المنتج. يتناول هذا المقال القرارات الهندسية التي تُبقي واجهات الويب السحابية قابلة للتوسّع ومتاحة للجميع: أين نرسم حدود المكوّنات، وكيف نمثّل حالات البيانات، وكيف نجعل إمكانية الوصول خاصية من خصائص النظام لا خطوة مراجعة، وكيف نضع ميزانيات أداء للشاشات الغنية بالبيانات.

تستند الأمثلة إلى دراستَي حالة مجهولتَي الهوية في هذا الموقع: [مركز تحكّم تحليلي](/ar/work/analytics-command-center/) و[تطوير نظام تصميم](/ar/work/design-system-uplift/).

## لماذا تفشل الواجهات السحابية عند التوسّع

تضع المنتجات السحابية الواجهة الأمامية تحت ضغط غير مألوف. تصل البيانات بشكل غير متزامن، وغالبًا من عدّة خدمات تختلف في زمن الاستجابة وطريقة الإخفاق. يملك المستخدمون أدوارًا وصلاحيات مختلفة. وتبقى الشاشات مفتوحة طويلًا: يترك الناس لوحة البيانات مفتوحة لساعات ويتوقّعون أن تبقى محدَّثة دون إعادة تحميل.

تحت هذا الضغط تتكرّر أنماط الإخفاق نفسها:

- **كل رقم يبدو بالأهمية نفسها.** حين تتنافس المؤشّرات الملخّصة والرسوم البيانية والمرشّحات والجداول على الانتباه، لا يعرف المستخدم ما الذي تغيّر ولا ما الخطوة التالية.
- **تُصمَّم الحالة المثالية وحدها.** تُعالَج حالات التحميل والفراغ والاكتمال الجزئي والبيانات القديمة والخطأ حالةً بحالة، فتتصرّف كل لوحة بطريقة مختلفة عندما تتأخّر البيانات أو تغيب.
- **تتحوّل الأدوار إلى نسخ متفرّعة.** يحصل كل مستوى صلاحيات على نسخة خاصة من الشاشة، ثم تبتعد النسخ عن بعضها.
- **تفقد المكوّنات المشتركة ثقة الفريق.** حين يتصرّف زر أو بطاقة مشتركة بشكل غير متّسق، تبني الفرق نسخًا محلية بدل إصلاح الأصل.
- **يتراجع الأداء لوحةً بعد لوحة.** لا يكون أي تغيير بطيئًا بمفرده، لكن الصفحة تراكم العمل حتى يتأثّر الرسم الأول والتفاعل معًا.

بدأت دراسة حالة مركز التحكّم التحليلي من وضع مشابه. كانت المعلومات المترابطة موزّعة على عروض منفصلة، ما أبطأ المقارنات وزاد احتمال تفويت حالات مهمّة. لم يكن الحلّ تجديدًا بصريًا، بل مجموعة من القرارات المعمارية.

## معمارية مكوّنات تصمد أمام النمو

تفصل معمارية المكوّنات القابلة للتوسّع بين ثلاث مسؤوليات يسهل خلطها: تشكيل البيانات، واختيار الحالة المعروضة، ثم تصييرها.

يشمل تشكيل البيانات التجميع والتصفية والتنسيق وحساب القيَم المشتقّة. مكانه خارج مكوّنات العرض. إذا كان مكوّن الرسم البياني يجلب بياناته ويحوّلها أيضًا، فلا يمكن إعادة استخدامه لدور آخر ولا اختباره دون شبكة. لهذا السبب فُصلت مكوّنات العرض عن منطق تشكيل البيانات في دراسة حالة المركز التحليلي، فبقيت شيفرة الواجهة قابلة للصيانة مع إضافة وحدات جديدة.

اختيار الحالة هو الحدّ الثاني. لكل لوحة تعتمد على البيانات في واجهة سحابية أكثر من حالتين. تعامَل معها كعقد صريح لا كمجموعة من القيَم المنطقية:

```tsx
import type { ReactNode } from 'react';

type PanelState<T> =
  | { status: 'loading' }
  | { status: 'populated'; data: T; updatedAt: Date }
  | { status: 'filtered-empty'; activeFilters: string[] }
  | { status: 'unavailable'; reason: 'permission' | 'not-configured' }
  | { status: 'error'; retry: () => void };

interface PanelBodyProps<T> {
  state: PanelState<T>;
  render: (data: T, updatedAt: Date) => ReactNode;
}

export function PanelBody<T>({ state, render }: PanelBodyProps<T>) {
  switch (state.status) {
    case 'loading':
      return <PanelSkeleton />;
    case 'populated':
      return render(state.data, state.updatedAt);
    case 'filtered-empty':
      return <EmptyState filters={state.activeFilters} />;
    case 'unavailable':
      return <UnavailableNotice reason={state.reason} />;
    case 'error':
      return <ErrorNotice onRetry={state.retry} />;
  }
}
```

يجعل الاتحاد المميَّز التركيبات المستحيلة غير قابلة للتمثيل. لا يمكن أن تكون اللوحة في حالة تحميل وخطأ في آنٍ واحد، ويُنبّه TypeScript إلى أي حالة غير معالَجة عند إضافة حالة جديدة. كما يمنح مراجعة الشيفرة سؤالًا محدّدًا: هل تعالج هذه اللوحة كل حالات العقد؟ استخدمت دراسة حالة المركز التحليلي عقدًا مشابهًا (التحميل، والبيانات المعروضة، والفراغ بسبب المرشّحات، وعدم الإتاحة، والخطأ) للحدّ من مفاجآت التصيير الشرطي بين الوحدات.

لاحظ أن «الفراغ بسبب المرشّحات» و«عدم الإتاحة» حالتان مختلفتان. عبارة «لا نتائج لهذه المرشّحات» تدعو المستخدم إلى تغيير المرشّحات. أما «لا تملك صلاحية الوصول إلى هذه البيانات» فلا ينبغي أن تفعل ذلك. ودمجهما في حالة فراغ عامّة ينتج إرشادات مضلِّلة.

المسؤولية الثالثة هي التصيير، وتقدّم دراسة تطوير نظام التصميم قاعدة مفيدة: تعامَل مع المكوّنات المشتركة كبنية تحتية للمنتج لا كمعرض للمكوّنات. يحتاج كل مكوّن مشترك إلى عقد مستقر يحدّد ما يصيّره، وأي الحالات يمتلكها، وما يبقى قابلًا للتركيب، وأي القرارات تنتمي إلى شاشات المنتج. عندها يُعبَّر عن اختلاف الأدوار بالتركيب والصلاحيات لا بشاشات مستنسخة.

من الحدود العملية في الواجهات السحابية:

- بطاقات ملخّصة تمتلك القيمة ومقارنتها ووصفها المتاح
- لوحات رسوم بيانية تمتلك العنوان وملخّصًا نصيًا وعقد الحالات السابق
- أشرطة مرشّحات تحفظ حالتها في الرابط (URL) لمشاركة العروض واستعادتها
- جداول تمتلك الفرز والتحديد والتقسيم إلى صفحات

لمعالجة أوسع للحدود والرموز التصميمية وملكية الحالة، اقرأ [أفضل ممارسات الواجهة الأمامية لواجهة نظيفة وقابلة للتوسّع](/ar/blog/frontend-best-practices-clean-ui/).

## إمكانية الوصول كخاصية للنظام

في واجهة كبيرة، لا يمكن أن تعتمد إمكانية الوصول على تذكّر كل مهندس لكل قاعدة في كل شاشة. يجب أن تعيش في الطبقة المشتركة، بحيث يكون التنفيذ الصحيح هو الخيار الافتراضي أيضًا.

المكوّنات المشتركة هي أفضل مكان لذلك، لأن نمطًا قويًا واحدًا يمنع عيوبًا متكرّرة كثيرة. في تطوير نظام التصميم، استخدمت المكوّنات التفاعلية العناصر الدلالية قبل السلوك المخصّص، وبقيت أنماط التركيز المرئي متّسقة عبر السمات والحالات، ودعمت عناصر النماذج العناوين والأوصاف ورسائل التحقّق والحالات المعطّلة. ولم يكن اللون وحده إشارةً إلى حالات الحذف أو التحذير أو التحديد أو الخطأ.

يحتاج عرض البيانات المرئي إلى عناية خاصة. الرسم البياني تمثيل واحد للبيانات، لا المصدر الوحيد لمعناها. في دراسة حالة المركز التحليلي، تضمّنت لوحات الرسوم البيانية عناوين وصفية ونصوصًا داعمة، وحيثما أمكن لنمط بصري أن يخفي المعنى عن مستخدمي لوحة المفاتيح أو التقنيات المساعِدة، قدّمت الواجهة ملخّصات نصية أو قيَمًا منظَّمة مجاورة.

تعني إمكانية الوصول على مستوى النظام في لوحات البيانات السحابية ما يلي:

- **تصف العناوين بنية لوحة البيانات**، ليتنقّل مستخدمو قارئات الشاشة بين الأقسام.
- **لكل رسم بياني مكافئ نصي**: ملخّص للاتجاه أو جدول بالقيَم الفعلية.
- **تُعلَن التحديثات الخلفية بهدوء** عبر منطقة حيّة (live region) دون تحريك التركيز.
- **تشرح حالات الفراغ والخطأ ما حدث** وما يمكن للمستخدم فعله بعد ذلك.
- **تبقى مسارات لوحة المفاتيح متوقَّعة** عبر المرشّحات والجداول ونوافذ الحوار، مع تركيز مرئي في كل لحظة.

اجعل هذه الخصائص جزءًا من معايير قبول المكوّنات وادعمها بفحوص آلية. فحص axe في اختبارات end-to-end لا يثبت أن الواجهة قابلة للاستخدام، لكنه يمنع عودة العيوب المعروفة.

## ميزانيات الأداء للوحات البيانات الكثيفة

تحوّل ميزانية الأداء عبارة «لوحة البيانات بطيئة» إلى حدّ يجتازه التغيير أو يفشل فيه. للميزانيات الموجَّهة إلى المستخدم، ابدأ بعتبات Core Web Vitals مقيسةً عند المئين 75: أن يكون Largest Contentful Paint خلال 2.5 ثانية، وInteraction to Next Paint خلال 200 مللي ثانية، وأن يبقى Cumulative Layout Shift أقل من 0.1.

تهدّد الواجهات الكثيفة البيانات كل مؤشّر بطريقة متوقَّعة:

- **LCP** يتراجع حين ينتظر أول محتوى ذي معنى كل اللوحات. صيِّر طبقة القرار أولًا (القيَم الملخّصة وبنية الصفحة)، وتعامَل مع اللوحات المكلفة كإفصاح تدريجي. لهذا السبب قدّمت دراسة حالة المركز التحليلي المحتوى الملخّص الظاهر على لوحات التحليل العميق.
- **INP** يتراجع حين يعيد تغيير مرشّح تصيير الصفحة كلها، أو حين يصيّر جدول آلاف الصفوف دفعة واحدة. أبقِ حدود المكوّنات صغيرة بما يكفي لتجنّب سلاسل إعادة التصيير، واستخدم الافتراضية (virtualization) للجداول الطويلة، وأخرِج الحسابات الثقيلة من معالجات الأحداث.
- **CLS** يتراجع حين تختلف أحجام حالتَي التحميل والبيانات المعروضة. احجز مناطق ثابتة للبطاقات والجداول والرسوم البيانية، لتصل البيانات دون أن تزيح التخطيط.

أضِف ميزانيات هندسية إلى جانب ميزانيات المستخدم:

- ميزانية JavaScript لكل مسار تُفحَص في التكامل المستمر
- سبب معلَن لكل اعتمادية جديدة
- حدّ لعدد الطلبات التي يمكن أن تؤخّر أول تصيير ذي معنى
- حدّ أقصى لعدد الصفوف المصيَّرة دون افتراضية

تطبّق دراسة حالة [تحديث الأداء](/ar/work/performance-modernization/) الفكرة نفسها على مستوى المنتج: أولويات أوضح للمحتوى الحرج واللوحات الثانوية والتفاصيل المؤجَّلة، مع أنماط تحميل مستقرّة تقلّل حركة التخطيط التي يمكن تجنّبها.

لا تنجح الميزانيات إلا إذا فُحصت باستمرار. أدرِجها في المراجعة: تُبيّن [قائمة مراجعة الشيفرة الأمامية](/ar/blog/frontend-code-review-checklist/) كيف تُربط قرارات التنفيذ بمؤشّرات LCP وINP وCLS قبل الإصدار.

## قائمة التحقّق

نادرًا ما تأتي الواجهات السحابية القابلة للتوسّع من قرار كبير واحد. إنها تأتي من قرارات صغيرة كثيرة تُتَّخذ باتّساق. استخدم هذه القائمة أثناء التصميم ومراجعة الشيفرة.

<li>مثِّل كل لوحة تعتمد على البيانات بعقد حالات صريح.</li>

<li>عبِّر عن اختلاف الأدوار بالتركيب والصلاحيات لا بشاشات مستنسخة.</li>

لا يتطلّب أي من هذه القرارات مزوّدًا سحابيًا أو إطار عمل بعينه. يتطلّب التعامل مع الواجهة كنظام له عقود وقيَم افتراضية وحدود: الانضباط نفسه الذي يُبقي الخادم موثوقًا.
